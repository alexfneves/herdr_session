## FAILURE MODE 1 — context exhaustion before writing (RESIZED lane, retry issued)

**What happened.** `U5b / T13 resize` ran **~545 minutes** and produced **zero files**:
`git log` showed no commit past base `254d5eb`, `git status --porcelain -uall` = **0 entries**,

**Diagnosis (from the session transcript, not assumed).** 63 tool calls — **55 `bash` + 8 `read`, and
not a single `write`/`edit`**. The last assistant turns are all planning prose ("Now let me write the
harness file and the four scenario files…"), and the session ends at a **`compaction` entry** with
`summary: "No prior history."` + `tokensBefore` — i.e. the context window was consumed by reading
`dev/resize_drive.py`, `src/main.odin`, `src/terminal/resize.odin` and `tests/pty/*` **in full**, and
the lane died at the exact instant it was about to write.

**This is the migration's most expensive non-product failure: hours of spend, zero assertions, and it
LOOKS like it is still working.** It is the same class of failure as a suite that goes green while
asserting less — invisible until someone checks the artifact.

**Rule for every lane, enforced in re-dispatch briefs:**
1. **Do not read any large file in full.** Targeted `grep` / `sed -n 'X,Yp'`. The orchestrator puts
   the needed facts in the brief so the lane does not have to go find them.
2. **Write the harness before tool call #20.** Compile, then one scenario file at a time.
3. **Commit after every compiling unit.** One context loss must never cost the whole task.
4. If a lane reports "completed" — **verify the artifact exists before believing it.**
   `git rev-list --count HEAD ^<base>` and `git status --porcelain -uall | wc -l`.

**Standing check for the orchestrator after every lane completes:**
```sh
cd /tmp/lane-<x> && git rev-list --count HEAD ^254d5eb && git status --porcelain -uall | wc -l
```
Both zero ⇒ the lane did nothing, regardless of what it reported.

## Facts harvested from the dead lane's reading (don't pay for them twice)

For `resize` / T13 — verified against source, so the retry needs no exploration:

- **Trace producer:** `tui_dump_trace` at `src/main.odin:1186`, gated on env `HS_TUI_TRACE=<path>`,
  written **once at exit** (mid-run file I/O would change the thing being measured).
- **Resize line** = `os.write_string(f, fmt.tprintf("resize {}\n", termhandoff.summary(&tui.coalescer)))`,
  where `summary()` (`src/terminal/resize.odin:175`) returns
  `"resizes=%d passes=%d max_run=%d ratio=%.1f too_small_paints=%d eintr=%d"`.
  So the on-disk line is `resize resizes=… passes=… max_run=… ratio=… too_small_paints=… eintr=…`.
  **The `resize ` prefix comes from `tui_dump_trace`, not from `summary()`.** Easy to get wrong.
- **Total line:** `total={}ms frames={} polls={} hits={} idles={} errs={} remote_fans={} local_ms={} first_paint_ms={}`.
- **Python parser shape to reproduce:** `line.startswith("resize ")`, split whitespace, read `key=<int>`.
  No regex in Odin (`core:regex` absent).
- **Too-small gate:** `MIN_COLS = 40`, `MIN_ROWS = 10` (`resize.odin:56-57`), `too_small()` at `:61`,
  `too_small_message()` at `:68`.
- **The `%`-only format string is deliberate** (Odin can't mix `{}` and `%`; `{:.1}` renders
  `%!(NO VERB)` in this toolchain). Freeze it.
- **Static `check()` callsites under-report.** `dev/resize_drive.py` has 35 static callsites
  (no_key 4, flood 11, too_small 9, selection_shrink 5, eintr 6) → ×3 reps = 105, but the measured
  hermetic floor is **123**. **Therefore floors must come from RUNNING the old suite, never from
  counting callsites** — loops multiply at runtime.
  Retry instruction: `BIN=<binary> REPS=3 ./dev/resize-smoke.sh` and read the per-scenario counts.
